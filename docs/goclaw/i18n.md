# Internationalization (i18n) — policy and future work

## Today (implemented)

- **Model replies:** The embedded base system prompt (`internal/orchestrator/base_system_prompt.md`) opens with **RESPONSE LANGUAGE** (see that file). Each request may append a **runtime user-language hint** at the end of the system prompt (`internal/orchestrator/user_language_hint.go` → `buildRequest`):
  - **`preferred_response_language`**: `auto` (default), `es`, `en`, `fr`, `de`, `pt`, or `from_os`. Fixed tags add a **settings** hint so replies default to that language; `from_os` uses `LC_ALL` / `LC_MESSAGES` / `LANG` as a **fallback** when text detection is unsure.
  - **`auto` / `from_os`**: order is **heuristic** (es/fr/de/pt markers) → **[whatlanggo](https://github.com/abadojack/whatlanggo)** when reliable → for `from_os` only, **locale env** primary tag.
  - Structured JSON-looking tool payloads skip the hint.
  Paths, commands, and code stay as the task needs. Env: **`GOCLAW_PREFERRED_RESPONSE_LANGUAGE`** (seeded in `config.Default()`; merged settings override).
- **Source code and static UI:** Per [CLAUDE.md](../CLAUDE.md), user-visible strings baked into Go (banners, `/capabilities`, onboarding, errors) remain **English** until a real i18n layer exists. That avoids mixing unmaintained translations in code.

## Future (not implemented)

Possible later steps, if the project adopts localized chrome:

- **`ui_locale` (or `LANG`)** in settings / env to select a catalog for static strings (TUI footer, readline banner, slash help, onboarding).
- **Message catalogs** (e.g. `internal/locale/` with `en`, `es`, …) or a small JSON/JSONL bundle per language—loaded once at startup.
- **Custom agent profiles** (`.goclaw/agents/*.md`) already let a user add “always reply in Spanish” (or any language) via `system_prompt` for a dedicated profile; that complements rule 8 above.

Track roadmap checkboxes in [roadmap.md](./roadmap.md) (Tier “Future — UI localization”).
