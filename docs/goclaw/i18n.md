# Internationalization (i18n) — policy and future work

## Today (implemented)

- **Model replies:** The embedded base system prompt (`internal/orchestrator/base_system_prompt.md`) instructs the assistant to **match the user's natural language** for conversational prose (e.g. Spanish in → Spanish out), while keeping paths, commands, and code as the task needs. No separate language detector is required—the LLM follows the rule from context.
- **Source code and static UI:** Per [CLAUDE.md](../CLAUDE.md), user-visible strings baked into Go (banners, `/capabilities`, onboarding, errors) remain **English** until a real i18n layer exists. That avoids mixing unmaintained translations in code.

## Future (not implemented)

Possible later steps, if the project adopts localized chrome:

- **`ui_locale` (or `LANG`)** in settings / env to select a catalog for static strings (TUI footer, readline banner, slash help, onboarding).
- **Message catalogs** (e.g. `internal/locale/` with `en`, `es`, …) or a small JSON/JSONL bundle per language—loaded once at startup.
- **Custom agent profiles** (`.goclaw/agents/*.md`) already let a user add “always reply in Spanish” (or any language) via `system_prompt` for a dedicated profile; that complements rule 8 above.

Track roadmap checkboxes in [roadmap.md](./roadmap.md) (Tier “Future — UI localization”).
